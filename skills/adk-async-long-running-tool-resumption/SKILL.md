# ADK Asynchronous Long-Running Tool Resumption

Use this skill when an agent in an ADK workflow must initiate external tasks that take
seconds to hours (video generation, batch inference, model fine-tuning, complex data
compilations, external human reviews) without blocking server worker threads or risking
socket timeouts.

## When to Use

- An agent tool invokes an operation taking more than a standard HTTP timeout (>30 seconds)
- Preventing idle compute and thread starvation in serverless environments (Cloud Run, Cloud Functions)
- Requiring reliable execution recovery across process restarts or network disconnects
- Implementing the Universal Resumption Pattern to handle both human input gates and long-running tools identically

---

## Core Mental Model: The Universal Resumption Pattern

In Google ADK, **Human Decision Gates** and **Long-Running Tools** share the exact same underlying suspension and resumption architecture:

| Dimension | Human Decision Gate | Long-Running External Tool |
|:---|:---|:---|
| **Initiating Construct** | `yield RequestInput(...)` inside function node | Function wrapped in `LongRunningFunctionTool(...)` returning `{"status": "pending"}` |
| **Suspension State** | Open interrupt in session store (`sessions.db`) | Open tool call in session store (`sessions.db`) |
| **Process Behavior** | Turn finishes, runtime halts, process exits | Turn finishes, runtime halts, process exits |
| **Resumption Part** | `Part(function_response=FunctionResponse(id=interrupt_id, name=..., response={...}))` | `Part(function_response=FunctionResponse(id=call_id, name=..., response={...}))` |
| **Engine Action** | Resumes immediately at downstream node | Delivers output to model or downstream node without re-executing completed nodes |

In both cases, execution pauses cleanly without keeping idle threads alive. Resumption occurs only when an external actor submits a `FunctionResponse` matching the recorded call identifier.

## Step-by-Step Procedure

### 1. Structure the Long-Running Tool Function

The tool function must initiate the asynchronous job with the provider and return immediately with an operational receipt:

1. Request the upstream provider to launch the asynchronous operation.
2. Extract the provider's external operation identifier or tracking token.
3. Return a dictionary containing `"status": "pending"` along with any operation metadata needed by downstream listeners.

```python
def render_submit(prompt: str) -> dict:
    """Submit a long-running generation job.

    Returns immediately with a pending status receipt. The final artifact
    is delivered asynchronously by external poller or webhook.
    """
    receipt = videogen_client.start_operation(prompt)
    return {
        "status": "pending",
        "operation": receipt["operation_name"],
        "prompt": receipt["prompt"],
    }
```

### 2. Wrap the Function with `LongRunningFunctionTool`

When declaring the agent node, wrap the function with ADK's `LongRunningFunctionTool`:

```python
from google.adk import Agent
from google.adk.tools import LongRunningFunctionTool

render_desk = Agent(
    name="render_desk",
    model=config.MODEL,
    instruction="Submit the production script for rendering using render_submit.",
    tools=[LongRunningFunctionTool(render_submit)],
)
```

**What the runtime does**: When the tool returns `"status": "pending"`, the ADK execution engine intercepts the turn, marks the tool call as pending, records the `call_id` in the active session store (e.g. SQLite `sessions.db`), and suspends the workflow graph.

### 3. Track Suspension Call Metadata

Ensure your persistence layer records:
- `session_id`: Active session identity
- `call_id`: The ADK tool call ID generated by the engine
- `operation_id`: External provider job ID
- `tool_name`: Name of the tool (e.g., `"render_submit"`)

In multi-tenant or serverless setups, write this receipt to a database table or message queue that external background pollers can query.

### 4. Build the Independent Delivery Daemon / Webhook Handler

Create a decoupled process (background worker, cron poller, or webhook endpoint) that watches external job completion without involving the ADK runtime:

```python
import asyncio
from google.genai.types import FunctionResponse, Part
from google.adk import Runner

async def deliver_completed_task(session_service, runner, pending_record):
    call_id = pending_record["call_id"]
    tool_name = pending_record["name"]
    session_id = pending_record["session_id"]
    user_id = pending_record["user_id"]

    # 1. Poll external provider until completed
    result = await check_provider_status(pending_record["operation_id"])

    # 2. Package the resumption event part
    resumption_part = Part(
        function_response=FunctionResponse(
            id=call_id,
            name=tool_name,
            response={"status": "completed", "result_url": result["url"]},
        )
    )

    # 3. Resume the workflow via run_async
    async for event in runner.run_async(
        user_id=user_id,
        session_id=session_id,
        new_message=resumption_part,
    ):
        handle_workflow_event(event)
```

### 5. Wire the Workflow Graph for Post-Resumption State Commit

After resumption, the graph advances to the next node in the edge tuple. Add a terminal or processing function node (e.g., `store_video`) to commit the newly delivered external artifact into shared session state:

```python
def store_result(node_input):
    # node_input contains the payload delivered in FunctionResponse
    result_url = node_input.get("result_url")
    yield Event(state={"final_artifact_url": result_url})

edges = [
    # ... prior nodes ...
    (scripter, render_desk, store_result),
]
```

## Environment & Implementation Caveats

- **Mocking for Fast Local Verification**: For unit testing and local CI, support a mock execution mode (e.g., `MOCK_ASYNC=1`) where the submit function returns a simulated receipt, and a fast background task delivers the `FunctionResponse` in 1–2 seconds.
- **Session Service Reliability**: Use `DatabaseSessionService` (PostgreSQL, Cloud SQL, or persistent SQLite) rather than in-memory storage (`InMemorySessionService`). In-memory sessions are lost whenever worker processes recycle or scale to zero.
- **Idempotent Delivery**: If delivery fails midway through `run_async`, ensure the background daemon does not repeatedly dispatch conflicting resumption events. Check if the session is already in a completed or advancing state.

---

## Edge Cases & Failure Modes

1. **Stale or Lost Call ID**: If the background worker loses the original `call_id`, ADK cannot route the `FunctionResponse` to the suspended node, causing the workflow to remain permanently stuck in `pending`. Always persist the `call_id` atomically when the tool function returns.
2. **Provider Failure Handling**: If the external operation fails (e.g., rendering GPU error), deliver a `FunctionResponse` with an error payload (`{"status": "failed", "error": "Out of memory"}`) rather than abandoning the job. This lets downstream router nodes navigate to remediation branches.
3. **Double Submission on Crash**: If the server crashes after the external job is launched but before the pending state is journaled, restarting the step will launch a duplicate job. Design external operations to accept idempotency keys derived from `session_id` and node name.
